# AGENTS.md: dotfiles

Operational digest for coding agents working in this repository.

This is the chezmoi source state of the user's Linux workstations (main machine: Kali Rolling, KDE Plasma 6 on X11, zsh, laptop).
It is the base layer of cles-en-main (`cem`, `~/Work/cles-en-main`), a workstation lifecycle tool built on chezmoi and mise.
The GitHub repository is **public**.

## Read first, in a fresh session

1. This file.
2. `openspec list`, then the change you are asked to work on under `openspec/changes/<change>/` (proposal, design, specs, tasks).
3. The findings that change cites in `docs/audits/2026-10-30-environment.md` (identifiers `F01`, `F02`, ...).
4. When the change names a cem checklist item: `~/Work/cles-en-main/migrations/2026-10-omalap-to-ulap01/checklist.md`.

`chezmoi source-path` prints `<repository>/home`; templates reach source files through `{{ .chezmoi.sourceDir }}`.
The audit and changes written before `adopt-chezmoiroot` use flat paths: prefix them with `home/`.

## Commands

- `chezmoi status` and `chezmoi diff --exclude=externals`: what an apply would change.
- `chezmoi apply --dry-run --verbose`: full preview, scripts included.
- `chezmoi status --include=scripts`: the scripts an apply would run (`R`); a script that renders empty is not listed.
- `chezmoi apply --exclude=scripts <target>`: apply one target without running scripts.
- `chezmoi execute-template < file.tmpl` and `chezmoi cat <target>`: render a template or a target.
- `chezmoi managed`, `chezmoi unmanaged <dir>`, `chezmoi doctor`.
- `zsh -n <file>`, `bash -n <file>`, `shellcheck <file>`: shell checks.
- Testing a script without running it: render it with `chezmoi -S <worktree> execute-template < home/.chezmoiscripts/<script>.tmpl`, then run the text with `CHEZMOI_SCRIPTS_DRY_RUN=1`, which makes every script print the change it would make instead of making it (read-only queries still run).
  Never set that variable on `chezmoi apply`: chezmoi records a script as run once it exits 0, so the real apply would skip it afterwards.
  The helper warns when it sees both.
- The proof of the shell code is the bats suite under `tests/`: `mise run test` runs the unit and smoke levels in a scratch home and writes a JUnit report to `tests/.reports/`, and `mise run test:live` adds the read-only tests that read this machine.
  `tests/README.md` describes the levels, the isolated and live read-only modes of the install-script harness, and the opt-in variables.
- Scripts look for their tools in the directories of `tools.search` (`home/.chezmoidata/tools.yaml`); to add directories or replace the list on one machine, set `extra` or `override` in the local config under `[data.tools.search]`, never in the data file.
- `home/dot_config/pipx/packages.json` holds no path and no interpreter; refresh it with the `pipx list --json | jq` command in the header of `home/.chezmoiscripts/run_onchange_after_12-pipx.sh.tmpl`.
- `openspec validate --all --strict`: check specs and changes.
- `mise run hooks:install`: after a fresh clone, install the pre-commit secret scan as a `.git/hooks` shim, which every git version runs.
- Startup time: GNU `time` is not always installed (distribution package `time`), so put `date +%s.%N` around each run of `zsh -i -c exit` and `zsh -l -i -c exit`, alternate the shell kinds, take the median of at least 7 runs (startup varies by hundreds of milliseconds between runs minutes apart), and run them under a pseudo-terminal (`script -qec 'zsh -i -c exit' /dev/null`) so that the line editor integrations load as in a terminal.
  `SHELL_RC_DEBUG=1` prints one debug line per startup file on standard error, and `SHELL_COMPLETION_REFRESH=1` regenerates the cached completion scripts at the next start.
- Agents started from an interactive shell, by hand or by herdr, run through the `opencode` function of `home/dot_config/shell/rc.d/445-tools_opencode.sh`, which removes the exported variables with secret-looking uppercase names from their environment (the pattern lives in that file and the names are computed at each call).
  `command opencode` runs the real binary with the full environment: the user types it, an agent never does.
- chezmoi comes from brew.
  Interactive shells and non-interactive login shells (`zsh -l -c`, `bash -l -c`, the desktop session) load brew through the environment part (the `env_` files of `rc.d`); non-interactive non-login shells (an ssh command, cron, `bash -c`, `env -i`) do not: run `eval "$(/home/linuxbrew/.linuxbrew/bin/brew shellenv)"` first, or call `/home/linuxbrew/.linuxbrew/bin/chezmoi`.
- The session umask is 0027, from the login: the `umask=` entry of the account's comment field, set by `run_onchange_before_03-session-defaults.sh.tmpl`, which also gives sudo a umask of 022 (`/etc/sudoers.d/50-umask`), the home mode 0700 and the generated locales; no startup file sets a umask, so files an agent creates are 0640 (directories 0750).
  Run that script only through its dry run (`CHEZMOI_SCRIPTS_DRY_RUN=1`) unless the user is present with sudo; `CHEZMOI_SCRIPTS_FORCE=1` installs the sudoers file without comparing it.

## Safety rules

- A full `chezmoi apply` needs a reviewed dry run and the user present: review `chezmoi apply --dry-run --verbose` with the user first, then run it in a terminal where sudo can ask for a password.
  The install scripts are idempotent since `make-install-scripts-idempotent`, but an apply also writes every target that drifted from the source (audit F13 to F15): the first one on the laptop is the supervised apply of `reconcile-drift-and-supervised-apply`.
- Apply single targets with `--exclude=scripts`.
- `chezmoi apply -R` also pulls into `~/.config/nvim`, fast-forward only, after asking for confirmation (chezmoi expects mode 0750 there, git made it 0775); `--force` skips the question, so run it only when the Neovim work is idle.
- Edit the source, never the target, for managed files; bring live edits back with `chezmoi re-add` after a diff review.
- Keys are not in the environment of a new shell: `secrets load` (`rc.d/446-tools_secrets.sh`) exports the private environment file into the calling shell and its children, `secrets unload` removes them and `secrets` alone prints how many are set.
  The user types `secrets load`; an agent never does.
- Never print, log or commit secret values; encrypted files are added with `chezmoi add --encrypt` and keep the `private_` attribute.
  Compare secrets by hash in memory, never by value, and never print a masked form either: a masked display keeps the last characters.
  To discard the standard output of a command in a pipe, write `cmd 2>/dev/null | next`: in zsh, `cmd 2>&1 >/dev/null | next` also sends standard output into the pipe (MULTIOS).
  Removing a secret from the file that sets it does not remove it from processes that inherited it: check the parents (`grep -c` on `/proc/<pid>/environ`, counts only), and unset it in the shell startup.
- Raw session exports contain private data: keep them in a scratch directory with mode 0700, commit only the redacted copies in `memory/sessions/`, and delete the raw files.
- Anything that uses sudo, writes outside `$HOME`, uninstalls or deletes needs the user's explicit go.
- Commits: propose the messages, commit only after the user validates them, never push without being asked.
- The brew hook (`home/dot_config/shell/rc.d/110-pkg_brew.sh`) commits the Brewfile by itself after brew changes: expect those commits.

## Writing for a public repository

- No secret values, no token scopes, no private hosts or IP addresses, no employer or client details.
- Names of secret variables: only publicly well-known ones, the names a provider documents as its convention and that public repositories already carry in the thousands.
  A name specific to this workstation, or chosen by the user, stays out: it tells what is set here.
  When in doubt, leave the name out and describe the variable instead.
  Values stay secret whatever the name.
- Open security issues are described in general terms, with a command that shows the details locally.
- The same rule applies to cem, which will become public too.
- Sibling repositories: name only those that are public or meant to be (darse, cem, bosco, greffe, opencode-readonly-guard, the Neovim configuration repository); call any other "a fleet repository".
  A file that is committed here is public, so a private repository is not named even to say that it is private.

## Conventions

- Commits: `type(domain:subject): imperative lowercase summary`, English, subject at most 80 characters; domains in use include `shell`, `pkg`, `dev`, `term`, `git`, `chezmoi`, `sys`, `editor`, `kde`; for this repository's own process use `chezmoi:spec`, `chezmoi:audit`, `chezmoi:docs`.
- Markdown: one sentence per line, no em or en dashes, no emoji, sentence-case headings, vim modeline as the last line.
- Shell: POSIX-compatible where both bash and zsh source the file; shell-specific code goes in `case "$CURRENT_SHELL"` blocks.
  An agent's shell is zsh, and four habits from bash fail there: a bare `echo ==` (equals expansion), two `<` redirections on one command (zsh concatenates them), an unmatched glob (the whole command aborts), and a variable holding a command with arguments (zsh does not split it: use an array or `${=var}`).
- Install priority for tools: mise, brew, apt, vendor APT repository, Flatpak; GitHub `.deb` releases through bin.

## Workflow

One OpenSpec change per working session.
`/opsx-apply <change>` to implement, `/opsx-verify <change>` to check, `/opsx-archive <change>` when done; then tick the cem checklist line named in the audit's change map.
New work starts with `/opsx-propose` or `/opsx-explore`.

Orchestration state lives in `.state/` of the checkout, as in the other fleet repositories, not in `/tmp/opencode`: it survives a reboot, an agent reads it without a permission prompt, and it is never committed (the ignore rule is a `.gitignore` line).
- `briefs/<name>/`: what an orchestrator sends to an agent.
  A brief for an agent that works in a worktree is written into that worktree's own `.state/briefs/`, because an agent that must read outside its own directory stops at a permission prompt nobody answers; the prompt that points at it carries an absolute path inside the worktree.
- `tmp/`: scratch of the checkout, mode 0700, for what a session needs and does not keep.
  Raw session exports are the exception: they stay in a scratch directory outside the repository until they are redacted and deleted.
- `journal.md`: append-only log, one line per event (briefs written, prompts sent, worktrees created and removed, merges, pushes): `- YYYY-MM-DD HH:MM:SS <actor> <event>`.
- `git worktree remove` deletes the ignored files of a worktree with it: a brief that must last is copied into its change folder, and nothing else lives only in a worktree's `.state/`.
- Ignored files are not scanned by the commit hook, so a brief or a journal never holds a secret value.

An agent that works a change (a lead, a builder, a closer) is finished when its work is merged or handed over and its session is exported.
Then its tab or workspace is closed by id and, when it had a worktree, the worktree goes with `scm:worktree:done <branch>`; the orchestrator does both, after the export is committed and pushed (`done` refuses while the branch is not in `origin/main` or an untracked file is left).
A worker is opened as a linked worktree workspace of the primary workspace of the repository (`herdr worktree open --workspace <primary>`), so that herdr groups it; it is closed with `herdr workspace close <id>`, never with `--group`, which also closes the primary workspace and every other worker.
A tab opened with `scm:worktree:new --tab` is closed with `herdr tab close <id>` and `done --keep-tab`.
A finished agent is not left open: it holds a context nobody uses, and a stale pane has been mistaken for a live one.
