## Why

`fast-correct-shell-startup` was narrowed on 2026-11-16 to the part that makes shell startup silent and fast.
What it left out is the half that decides what environment a shell provides: `PATH`, locale, which secrets are exported and to whom, the shell's umask, and what a non-interactive login shell (the desktop session) loads.
Audit findings F18, F21, F23 and the environment points of F33.
The study of secrets held by the desktop session is inside this change (decided on 2026-11-20): `findings.md` holds it, `design.md` the decisions taken with the user on 2026-11-21.

## What moves in

From the draft of `fast-correct-shell-startup`, with their open questions:

- **Clean `PATH`** (F18): the requirement "Clean PATH" and the task "`PATH` helper (prepend without duplicates, keep inherited); `.local/bin` first; aqua fix".
- **Working locale** (F21): the requirement "Working locale" and the task "Locale defaults (no `LC_ALL`; no `setlocale` warning)".
- **Opt-in token exposure** (F23): the requirement "Opt-in token exposure" and the task "Token loader as decided; tools that need tokens tested".
  It is also the backlog study "Secrets held by the desktop session" in `TODO.md`, which says what the study must settle before any change.
- **Decisions to take with the user** (task 1.2 of the draft): the token exposure mechanism, the shell umask, the locale.
- **Smaller points of F33**: syntax highlighting loads last, the shell umask is decided.
- **The interactive guard of `shellrc`** (task 2.2 of the draft): it is commented out, and restoring it as drafted would stop the desktop session from loading anything, see below.

Bash login on a bare terminal (F22) stayed in `fast-correct-shell-startup`.

Added by the decisions of 2026-11-21:

- **Keys on demand**: a `secrets` function loads the private environment file into the calling shell; startup exports it nowhere.
- **Session defaults from the login**: umask 027 for the user's sessions through `pam_umask`, umask 022 for sudo, home mode 0700, `en_US.UTF-8` generated, all from one install script.
- **History under XDG state**, with a migration that loses nothing while old shells run.
- **Dead startup files removed**: the profiling stubs, two empty `rc.d` files, `zsh/zshrc` and `bash/bashrc`.

## What the review of 2026-11-16 found for this change

- **The desktop session is a login shell of this configuration.**
  The display manager runs `zsh /etc/sddm/Xsession`, which sources `~/.zprofile` (the same file as `~/.profile`) without being interactive, and the environment it leaves goes to the systemd user manager: every graphical process inherits what `rc.d` exports, tokens included.
  `fast-correct-shell-startup` leaves that pass as it is, so the session's environment does not change under it.
- **A better version of "`profile` is environment-only"** is the main design question here.
  As drafted it would give the desktop login a pass of about 40 ms instead of several seconds, but the session would lose what the interactive parts set (mise on `PATH`, tool variables), the private environment file would stay exported there, and a shell-local guard is needed so the environment part does not run twice in an interactive login shell.
  The user wants the better version designed here, together with the token study.
- **`rc.d/040-env_path_base.sh` replaces `PATH`** instead of keeping the inherited value, so the draft requirement "keep inherited entries" does not describe today's behaviour; the second pass of a login shell hid this because it started from the same base.
- **The live `rc.d` has two files that the source does not manage**; one of them is an old copy of `050-env_path_user.sh`, which prepends the user's bin directories a second time.
- **`rc.d/020-env_defaults.sh` forces `LC_ALL`**, and defaults `LANG` to `en_US.UTF-8`, which is not generated here: a shell started without `LANG` (`env -i`, a bare terminal, ssh) makes bash print `setlocale` warnings.
  The tests of `fast-correct-shell-startup` set `LANG` as the desktop session does, so this case stays out of their counts.

## Open questions (answered on 2026-11-21, see design.md)

Each answer is built by the change: the section named after it in `design.md` is the decision, `tasks.md` the work.

- Token exposure mechanism: a loader function in the current shell only (`secrets load`, typed by the user), with per-tool keys (key command, key file, wallet) as the target, recorded as follow-ups: the note for the Neovim repository was delivered and answered (2026-11-21 and 2026-11-24), and the per-tool keys and the `~/.zshenv` review are items of the backlog of `TODO.md`.
- Shell umask: none in the shell; 027 from the login for the user's sessions, 022 forced for sudo, home 0700, written by one install script.
- Locale: both: `en_US.UTF-8` generated by that same script, and no forced `LC_ALL`, missing inherited locales dropped, English messages through `LANGUAGE`.
- What a non-interactive login shell loads: the environment part only (`shell/environment`), and `shellrc` gets its interactive guard back; a managed `~/.zshenv` goes to the backlog.
- Order: the study is inside this change.

## Capabilities

### New Capabilities

- `shell-environment`: which environment a shell provides (`PATH`, locale, exported secrets, umask) and what each kind of shell loads.

### Modified Capabilities

- `shell-startup`: "Single load of the interactive configuration" and "Behaviour that a startup change must keep": a non-interactive login shell loads the environment part instead of an `rc.d` pass, and startup no longer exports the private environment file.
- `agent-environment`: "A herdr-started agent holds none of them": the live probe loads the keys in the pane's shell before it starts the agent.
- `install-scripts`: one requirement added, "Session defaults are set for the login": a script sets the umask of the login, the umask of sudo, the home mode and the generated locales, reads a sudoers file that only root can read through one sudo call, and changes nothing when a tool fails.
- `shell-test-harness`: "The three ported suites keep their strictness": the scenario table of `tests/README.md` also maps `shell-environment` and the scenarios of the other four capabilities that this change adds or changes.

- Deleted targets, each with an entry in `home/.chezmoiremove`, deleted only at the deployment and with the user's go: the old names of the six renamed files, `005-dbg_prof_enable.sh`, `995-dbg_prof_results.sh`, `130-pkg-flatpack.sh`, `200-lang_python.sh`, `~/.config/zsh/zshrc` and `~/.config/bash/bashrc`.
- A new install script, `run_onchange_before_03-session-defaults.sh.tmpl`, that writes outside `$HOME` with sudo (the comment field of the account, `/etc/sudoers.d/50-umask`, `/etc/locale.gen` and `locale-gen --keep-existing`), with its data `system.session` and the apt package `locales` (which provides `locale-gen`) in `home/.chezmoidata/packages.yaml`; its first run is the user's, in a terminal where sudo asks for the password, and it is tested only through stubs, never run for real by the build.
- The session of the desktop: no key, no `LC_ALL`, a smaller environment, umask 0027 and a home of mode 0700 after the next login; tools that read keys from the environment need `secrets load` first.
- `tests/`: new unit, smoke and live files, the mutants of this change, the fixtures and the options of the install-script harness (`-t`, `-M`, a `sudo` responder, five more stubs); `tests/README.md` with its scenario table.
- `AGENTS.md`: `secrets load` is typed by the user, the session umask comes from the login, and a non-interactive login shell loads the environment part (and brew with it).
- Depends on `fast-correct-shell-startup` (load order, single pass) and on the credential decisions already taken: the wrapper `add-agent-env-wrapper` stays as it is.
